Таким образом, базовое SEO старой версии есть, полноценного предварительно сгенерированного SEO каждой сущности не подтверждено. Новый `noindex` профилей/сезонов в root candidate — риск ухудшения относительно старого разрешения индексации; до релиза устранить и проверить пустые/invalid состояния. Сохранение baseline и корректность новых адресов — обязательный migration scope; массовую статическую генерацию сущностей и расширение sitemap оценивать отдельно, не объявлять их уже реализованными на V1. ## 3. Последовательность реализации

### Этап A — исходники и воспроизводимая сборка

1. Зафиксировать production revision и исходный снимок, проверить актуальный `origin/main`. Составить список изменений релиза и отделить постороннюю незавершённую работу без массового staging или сброса.
2. Сохранить поддерживаемые V1 HTML/SEO-входы в отдельном источнике, например `v1-source/`; определить владельцев общих JS/CSS и генераторов. Генерируемые root/EN/old HTML не использовать как входы своей сборки.
3. Сравнить frozen V2 runtime и канонический `app.js` по функциям и зависимостям. Для каждой разницы решить: включить в этот релиз либо оставить вне него. Сохраняются исправления пагинации, SR/санкций, событий и производительности.
4. Получить один согласованный канонический runtime, пересобрать адаптер штатным генератором, обновить manifest/hash и версии импортов. Убрать `ASG_V2_PRESENTATION_ONLY=1` как обход для release-сборки. Не исправлять несоответствие ручной заменой hash.
5. Сделать явный реестр страниц: route, screen, RU/EN, canonical, доступ, alias, V1-equivalent. Использовать его для генерации HTML, навигации, sitemap и проверки переходов.
6. Переработать `build-v2.mjs`, `v2/routes.js`, locale-resolver и V2/V1-переключатель для новой адресной схемы. Исходники V2 можно оставить в папках `v2`/`v2-source`; URL страницы не должен зависеть от имени папки реализации.
7. Обновить build/dist allowlist и release-проверки: root RU, `/en/`, `/old/`, новые разделы и исключённые рабочие потоки. Исследования, фикстуры, локальный прокси, исходники шаблонов и секреты не должны попасть в публичный артефакт.

Готовность: сборка повторяется из чистого согласованного source revision; hash runtime совпадает; исходный V1 интерфейс сохранён независимо от выхода генератора.

### Этап B — перенос старого интерфейса

1. Сгенерировать полноценные `/old/` и `/old/en/` с прежним интерфейсом и действующими данными.
2. Перенастроить V1 определение экрана/языка, абсолютные и относительные ссылки, breadcrumbs, auth return path, юридические ссылки, сообщения, новости и ссылки сущностей.
3. Навигация старого интерфейса остаётся внутри `/old/`; кнопка «Новый сайт» ведёт на эквивалент V2. В V2 кнопка «Старый сайт» открывает соответствующую старую страницу с тем же языком и сущностью.
4. Общие API и необходимое общее выполнение JS остаются доступны. Не копировать DOM с неизменёнными абсолютными ссылками и не переписывать адреса API под `/old/`.
5. Дать старым страницам `noindex,follow`, исключить из sitemap. Canonical на эквивалент новой страницы добавлять только там, где совпадает назначение; исключённые уникальные рабочие потоки не канонизировать на главную.

Готовность: старый интерфейс работает по прямому входу, с перезагрузкой, ссылками и Steam-сеансом; переключение версий не теряет выбранную сущность.

### Этап C — финальный аудит переходов V2

Проверить реестр всех мигрированных экранов: главная, Hourly, архив/результат, профиль и ELO/SR, список/детали/история чемпионатов, клубы/команды, машины, фан-статистика, баны, новости/статья, сообщество, инструкции/о проекте, документы/политики, кабинет/настройки, модерация, Portal Operations, 404.

1. Обход ссылок в генерируемом артефакте плюс обход ссылок после реального рендера данных. Первый не заменяет второй.
2. Для RU/EN проверить меню, профильное меню, футер, breadcrumbs, версии, языки, кликабельные пилоты/клубы/команды, race/result ссылки и вложенные модалки.
3. Проверить прямой вход и reload на каждой странице, entity query, календарь/месяц, пагинацию, фильтры, back/forward и восстановление родительской модалки/фокуса.
4. Проверить старые якоря `#championship`, `#bestlaps`, `#worst-safety`, `#clubs-teams-stats`, «О сервере» и новые якоря V2 через явную карту вкладок/секций.
5. Протестировать гостя, авторизованного пилота, модератора и оператора. Вернувшийся после Steam/Discord пользователь должен попасть на нужную новую/старую страницу. Не менять текущие backend-проверки доступа.
6. Найти остаточные ссылки на `/v2/ru/`, `/v2/en/`, `/ru/`, `/preview/`, localhost и демонстрационные сущности. В новой навигации они допустимы только как намеренные совместимые entry points или исключения, а не как основные переходы.
7. RU/EN содержимое: заголовки, статусы, формат гонки, модалки, формы, ошибки, даты/часовой пояс и документы. Юридическую политику показывать в действующей утверждённой редакции; не изобретать юридический перевод. Если официальный текст только русский, явно указать это на английской странице.
8. Проверить размеры 320, 390, 768, 1280 и 1920 px, раскрытые/скрытые виджеты, длинные названия, reduced motion и отсутствие горизонтального переполнения.

Результат: `route-audit.json`/таблица с исходным URL, переходом, конечным URL, языком, HTTP-статусом, сохранением query/hash и ошибками. Ноль неожиданных 404, пустых страниц, петель и JS-ошибок в проверенном scope.

### Этап D — совместимость URL и HTTP-редиректы

| Старый URL | Цель | Условие |
| --- | --- | --- |
| `/ru/<route>` | `/<route>` | RU, существующий эквивалент |
| `/v2/ru/<route>` | `/<route>` | Только страницы, не ресурсы V2 |
| `/v2/en/<route>` | `/en/<route>` | Только страницы |
| `/v2/` | `/` | Русский по умолчанию |
| `/preview/ru/<route>` | `/<route>` | Сопоставление по реестру Preview |
| `/preview/<route>` | `/en/<route>` | Прежний EN entry point, после проверки старой схемы |
| `/preview/` | `/` | Главная больше не является прототипом |
| `/index.ru.html` и прочие старые aliases | соответствующий canonical | Сначала учесть существующие aliases |
| `/events/?slug=…` | `/hourly/championship/?slug=…` | Сохранить сезон; EN-вариант — в `/en/` |
| `/hourly/privacy/`, `/hourly/cookies/` | `/privacy/`, `/cookies/` | Соответствующий EN язык сохраняется |

Текущие EN адреса без префикса, например `/cars/`, становятся RU адресами по явному требованию пользователя. Их нельзя одновременно перенаправлять на `/en/cars/`; иначе RU не будет работать. Английские страницы получают новый `/en/` canonical и парные hreflang.

Редиректы сохраняют query, включая `id`, `slug`, `event_id`, UTM, фильтры и страницу списка. Семантические fragment-якоря проверяются браузером: сервер их не получает. Каждый старый путь ведёт прямо на конечный эквивалент без цепочки `/ru/` → `/v2/ru/` → `/`.

На GitHub Pages HTML/JS-переход не равен HTTP 301. Рекомендуемая схема — настоящие редиректы в существующей Cloudflare-зоне; Single/Bulk Redirects требуют proxy для соответствующего DNS record. До применения проверить доступ к зоне, режим proxy, лимиты правил, HTTPS до origin и взаимодействие с имеющимися правилами. Не переносить весь сайт на VPS ради редиректов и не затрагивать subdomain API.

Не делать catch-all `/v2/*` → `/*`: это сломает `/v2/assets/`, `/v2/runtime/` и модули. Правила только для страниц, отдельно от JS/CSS/картинок и исключённых потоков. `/old/` не должен совпадать с правилами удаления прежних префиксов.

Перед переключением подготовить и проверить конкретный набор edge-правил, его экспорт/backup и rollback. Если доступ к edge-конфигурации отсутствует, frontend можно подготовить, но полноценный выпуск со сменой canonical URL и HTTP-совместимостью считать незавершённым.

### Этап E — удаление третьего сайта Preview

1. Выяснить зависимости `/preview/`, `build-preview.mjs`, `check-preview.mjs`, `refresh-preview-presentation.mjs`, `preview-presentation-policy.mjs`, manifest, components/runtime, npm scripts и release-тестов.
2. Удалить именно третий публичный сайт и его самостоятельную сборку/проверки; убрать `/preview/` из artifact allowlist и навигации.
3. Сначала сохранить в поддерживаемых V2-источниках всё, что реально используется V2. Проверка release не должна импортировать удалённый `preview/routes.js`.
4. Историю оставить в Git. Дизайн-исследования и нужный локальный `scripts/preview-v2.py` не являются третьим публичным сайтом. Preview/diff будущих гонок в Portal Operations также не удаляется.
5. Старые ссылки Preview направить на новые эквиваленты по таблице. Если эквивалента нет — корректный 404/410 через доступный hosting-механизм, без массового редиректа всех ошибок на главную.

Готовность: артефакт не содержит третьего интерфейса; CI не требует его сборки; новые страницы не загружают его ресурсы.

### Этап F — SEO и аналитика

**Поиск:**

1. Публичные root RU и `/en/` снять с `noindex`. Кабинет, настройки, модерация, Portal Operations, отсутствующие сущности и приватные/служебные экраны сохранить неиндексируемыми.
2. Canonical у публичной страницы ведёт на неё саму в правильном языке. Для сущности сохранить значимый `id`/`slug`; служебные UTM и случайные параметры не создавать как новые canonical.
3. Парные `hreflang="ru"`, `hreflang="en"`, `x-default` на русский canonical. Обе стороны ссылаются друг на друга. `html lang`, видимый текст и метаданные согласованы с адресом.
4. Сохранить и адаптировать title/description, доступный в HTML SEO-текст, WebSite/Organization JSON-LD, Open Graph/Twitter, favicons и verification-файлы. Не выпускать все страницы с метаданными главной.
5. Генерировать sitemap из того же реестра: существующие индексируемые RU/EN URL и, где доступны опубликованные стабильные идентификаторы, публичные страницы сущностей. Исключить `/old/`, `/preview/`, V2 aliases, кабинет/управление, поисковые фильтры и отсутствующие сущности. `lastmod` — реальные даты изменения, а не искусственное ежедневное обновление всех строк.
6. `robots.txt` оставляет доступ к публичным страницам и ресурсам, указывает production sitemap. Не блокировать обход `/old/` одновременно с ожиданием, что поисковик прочитает его `noindex`.
7. Несуществующий физический путь возвращает настоящий HTTP 404 и общую V2 страницу ошибки с рабочими ссылками RU/EN. Для отсутствующей динамической сущности в существующем static shell показать честное состояние и `noindex`; не выдавать клиентский экран ошибки за изменение HTTP 200 на 404.
8. Проверить статус/Location/конечный canonical всех aliases, `www`/HTTPS и отсутствие redirect loops. Не добавлять в sitemap URL, который сам редиректит.

**Аналитика:**

1. Сохранить счётчик Яндекс `107697834`, существующие параметры и единственную инициализацию на документ. Удалить любые demo-счётчики, если они найдутся при полном аудите.
2. Сохранить `asgPrivacyConsent`, cookie согласия, существующий формат/редакцию и настройки cookies. Проверить новый пользователь, разрешение, отказ, отзыв и уже сохранённый выбор. Перенос языка/версии не должен заново запускать счётчик или терять выбор.
3. Проверить цели по кнопкам/формам и условия по URL. Цели, привязанные к `/ru/` или старым селекторам, могут потребовать перенастройки существующего кабинета аналитики. Не обещать их сохранение только по совпадению counter ID.
4. Сохранить подтверждение Google Search Console. GA4/GTM подключать только после обнаружения действующего подключения или получения существующего ID; не создавать новый счётчик вместо неизвестного прежнего. Решение пока ожидается от пользователя.
5. В браузерных тестах проверить network/init и отсутствие дублей/запросов при отказе с перехватом обращений аналитики. После публикации проверить фактический запрос и, при доступе к кабинетам, поступление тестового посещения/целей в Метрику и GA4. HTTP 200 HTML не подтверждает попадание событий в отчёты.
6. Отправить обновлённый sitemap в существующие Search Console и Яндекс Вебмастер при наличии доступа, проверить URL Inspection/переобход. Так как домен не меняется, это изменение URL/языков внутри сайта, а не заявка на перенос домена.

## 4. Обязательные проверки кандидата

| Проверка | Условие выпуска |
| --- | --- |
| Полный `npm.cmd run ci` | Успешный verify, unit, build, references, dist/hash и HTTP smoke на согласованном revision, без пропуска runtime-теста |
| Route/SEO audit | Реестр покрыт; RU/EN и old переходы корректны; sitemap, robots, canonical/hreflang и verification сверены |
| Browser regression | Главная и все мигрированные группы, вложенные модалки, страницы результата, календарь, ELO/SR, доступ, ошибки и адаптив |
| Данные | Чтение настоящих опубликованных public данных; проверка недоступности/пустых/устаревших данных; нет fixtures в выдаче |
| Мутации | Голосование, изменения профиля, санкции и Portal команды проверяются на перехваченных запросах; реальных команд администратора как тест не отправлять |
| Аналитика | Counter/verification сохранены; consent и один init работают; оговорён отдельно доступ к отчётам и GA ID |
| Производительность | Нет новых idle polls/тяжёлой постоянной анимации; сравнение CPU/requests/loading desktop/mobile с нынешней V2 |
| Исключённые потоки | ASG Lab сохранил фактический Steam-допуск; командная регистрация сохранила URL, язык и действие |
| Публичный состав | Явный allowlist, нет secrets/local proxy/test data/design research; Preview удалён из release |
| Откат | Сохранены previous revision/artifact, таблица URL и edge-config; fallback проверен заранее |

Не исправлять тесты под новый маршрут без проверки нового поведения. Старые V1-specific DOM-тесты адаптировать к проверке V1 в `/old/`, а новые основного сайта проверяют V2 в root/EN.

**Согласование перед выпуском, запрошенное пользователем:** сначала предоставить готовый локальный release candidate по ссылкам с окончательной схемой адресов, отчёт по переходам/тестам, перечень включённых страниц и исключений, specification редиректов и способ отката. После пользовательской приёмки этой конкретной сборки и явной команды публикации выполнять этап 5. До согласования можно завершить всю локальную подготовку; текущий запрос на план не разрешает переключать production или удалять опубликованный Preview.

## 5. Публикация и приёмка

1. Сохранить immutable candidate artifact с source revision, SHA-256 inventory, URL map и backup edge-config. Подготовить предыдущую production версию и fallback старого интерфейса под **новыми** RU-root/EN URL.
2. Опубликовать полный набор страниц и ассетов согласованным site-release из `top/main`; удостовериться, что CI/deployment относятся к тому же commit. Backend, игровые серверы и notifier не обновляются этим релизом.
3. Исключить промежуток, когда новая HTML ссылается на отсутствующие файлы. Старые runtime/ассеты оставить на время совместимости; обновлять cache-версии изменённых ресурсов.
4. После появления содержимого на origin проверить root RU, `/en/`, `/old/`, `/old/en/`, основные разделы, error page, API read, consent и verification. Затем включить подготовленные redirect rules.
5. Для контролируемого приёмочного окна можно использовать временные 302 с коротким кэшем; после успешной проверки заменить на 301. До фиксации 301 все конечные URL и fallback должны быть проверены. Окончательный релиз не оставляет временные редиректы вместо постоянных.
6. Проверить edge и чистый браузер: HTML, JS/CSS/JPEG/SVG, RU по умолчанию при прежнем EN storage, EN direct entry, старые ссылки/query/UTM, Steam return, обе версии и исчезновение Preview.
7. Наблюдать ошибки frontend/API/asset delivery и поступление аналитики минимум 30 минут; дополнительно проверить 24–48 часов после перехода. Индексацию и 404 по старым ссылкам отслеживать в последующие недели; мгновенное сохранение поисковых позиций не обещать.
8. Итоговый отчёт: release commit, deployment status, рабочие адреса, фактические метрики, sitemap/robots, redirect audit и оставшиеся ограничения. «Готово» означает подтверждённую выдачу production содержимого, а не только push.

## 6. Откат

Триггеры: корень не открывается или имеет неверный язык, пустые данные, поломка авторизации, критические JS/asset ошибки, неприменимое согласие, петли редиректов либо массовые 404.

Для сайта — отдельный проверенный revert-коммит/повторная доставка предыдущего пригодного артефакта по действующему механизму; без force push и отмены чужих правок. Для edge — сохранённый отдельный набор правил. `/old/` как ссылка не заменяет реальный rollback.

Уже закэшированный 301 нельзя гарантированно отозвать у всех браузеров. Поэтому fallback старого интерфейса обслуживает RU в корне, EN в `/en/` и остальные новые целевые URL; aliases продолжают работать. Не вводить обратный `/` → `/ru/`, если клиент мог закэшировать `/ru/` → `/`: это создаёт петлю. Query/id/slug и данные сохраняются.

После отката перепроверить новые целевые URL, одну гонку/профиль, вход и consent; записать revision/время/причину. Редиректы старых ссылок сохранять длительно; Google рекомендует минимум год для постоянного переноса URL.

## 7. Открытые внешние зависимости

1. Доступ к существующей Cloudflare-зоне и фактическому delivery/deployment path: нужен для настоящих HTTP redirects и проверки их доставки. NS и public headers уже определены; настройки зоны ещё не проверены.
2. Google Analytics: сохранить только обнаруженные текущие подключения либо получить существующий `G-…`/`GTM-…`. Search Console подтверждение найдено и сохраняется независимо от решения.
3. Доступ к Метрике/Search Console/Вебмастеру для проверки отчётов, целей и отправки sitemap. Фронтенд/network проверки выполнимы без этих кабинетов; поступление событий в них нельзя объявить проверенным без доступа.

Это не требует разработки backend. До внешних настроек можно полностью подготовить и проверить локальный release candidate и reviewable redirect specification.

## Основания SEO/hosting

- [Google: перенос страниц и URL](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes) — карта URL, постоянные перенаправления, проверка sitemap/редиректов и длительное сохранение совместимости.
- [Google: локализованные версии](https://developers.google.com/search/docs/specialty/international/localized-versions) — отдельные языковые URL и взаимные hreflang.
- [Google: noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing) — поисковик должен иметь возможность обхода, чтобы увидеть noindex.
- [Cloudflare: HTTP redirects](https://developers.cloudflare.com/rules/url-forwarding/) — Single/Bulk Redirects, proxy requirement и ограничения текущего тарифа.
- [GitHub: Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) — статический сайт, отдельный от VPS API.
