## Подготовленные HTTP-правила

`node scripts/prepare-edge-release.mjs` создаёт в `C:/Python/asgracing/tmp/v2-edge-preparation/`:

- `edge-plan-302.json` и `edge-plan-301.json` — спецификации **выключенных** правил;
- `bulk-redirects-302.csv` и `bulk-redirects-301.csv` — CSV без заголовка;
- `inventory.json` — SHA-256 четырёх файлов, статус prepared-not-applied.

Одна Bulk Redirect List содержит 574 точных адреса: 287 маршрутов × корень/www. Source без схемы покрывает HTTP и HTTPS; target всегда HTTPS основного домена. Query сохраняется, subdomain/subpath/suffix matching выключены. Восемь Single Redirects обрабатывают гонки `race_id` → `id` и новости `slug` → `id`, отдельно RU/EN и положение ключа в query. Остальные параметры, включая повторные UTM и кодированные значения, сохраняются. Правила ограничены GET/HEAD и двумя hostname; API, остальные поддомены, ассеты, `/old/`, ASG Lab и native командная регистрация не перехватываются.

Single Redirects должны отработать до Bulk. Использован `wildcard_replace` вместо Business-only regex; конфликт существующего `id` оставлен клиентскому compatibility handler. Кодированные имена legacy-ключей тоже обрабатывает клиент, поэтому для таких редких входов возможен дополнительный переход в браузере. Дубли legacy-ключа сохраняются, первым считается первое значение. Fragment сервер не получает; его сохранение надо дополнительно проверить браузером на реальном edge.

Это спецификация для добавления к существующим rulesets, **не готовая команда замены всего ruleset**. Локальная модель не компилирует язык Cloudflare. Внешняя валидация выражений и доступная квота ещё не проверены: необходимы 8 Single rules, 1 Bulk rule, 1 redirect list и 574 записи сверх существующих.

Основания формата и порядка: [Cloudflare redirects](https://developers.cloudflare.com/rules/url-forwarding/), [Bulk matching](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/how-it-works/), [CSV](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/csv-file-format/), [функции выражений](https://developers.cloudflare.com/ruleset-engine/rules-language/functions/). Для выполнения этих правил соответствующие DNS records должны быть proxied.

## Экспорт и последующее включение

1. Получить текущую конфигурацию и подтвердить права/квоты. Подготовлен `scripts/audit-edge-config.py`: только GET, без обновления логина или API-записи. Он сохраняет zone/DNS/Page Rules, Single/Bulk rulesets, cache rules, redirect lists со всеми страницами элементов, SSL/HTTPS/cache settings и SHA-256 inventory в workspace `tmp/v2-edge-backups/<UTC>/`. Cursor-pagination списков соответствует [Cloudflare API](https://developers.cloudflare.com/api/resources/rules/subresources/lists/subresources/items/methods/list/). При недоступном endpoint экспорт помечается incomplete, а не успешным backup. Пока инструмент проверен синтаксически; полный реальный экспорт не выполнен.
2. Сопоставить существующие redirects, cache rules и новые URL: не менять чужие правила. Валидировать выражения в Cloudflare; при нехватке квоты пересмотреть проект до включения. Добавлять только ASG-owned правила и список в выключенном виде, записав назначенные IDs и порядок.
3. Подтвердить HTTPS до origin и существующий SSL. При включении proxy проверить Full (strict) с действительным сертификатом origin; не переключать автоматически в Flexible. Сохранить прежние DNS значения и proxy/SSL flags. Изменять только корень/www; auth/data/votes поддомены остаются вне этого переключения. Проверить, что существующий cache policy не удерживает старые HTML и не конфликтует с consent/auth.
4. Показать и согласовать финальный кандидат. Выполнить отдельную разрешённую публикацию из `top/main`; проверить фактические RU `/`, EN `/en/`, `/old/`, сущности, документы и ассеты на origin. До этого включение редиректов недопустимо: нынешний корень ещё имеет прежний языковой смысл.
5. После появления всех конечных страниц включить только подготовленные правила 302; проверить root/www × HTTP/HTTPS, legacy/Preview, ID/UTM, EN, native exclusions и отсутствие циклов. Статус 302 сам по себе не гарантирует отсутствие cache: проверить существующие response/cache настройки, заголовки и чистый браузер.
6. После приёмки переключить этот же набор на 301 и провести повторный HTTP/браузерный аудит. Записать правила, время, release revision и результат. Проверить sitemap/robots и кабинеты поисковиков, не удалять старые адреса из карты совместимости.

Включение proxy и правил — внешнее изменение после согласования кандидата/команды публикации. В текущем шаге выполнены только локальные файлы и read-only наблюдения.

## Аналитика и Steam

Браузерная проверка кандидата охватывает `/`, `/en/`, `/old/`, `/old/en/` × отсутствие согласия / прежний отказ / прежнее разрешение: 12 сценариев. Проверены cookie fallback в существующий localStorage, отсутствие загрузки Метрики до разрешения, один init после разрешения, повторное согласие без двойного init, отзыв с reload и удалением `_ym` cookie/storage. Реальные события не отправлялись: tag.js подменён заглушкой, внешние записи заблокированы.

На настоящем origin после публикации проверить поступление данных в существующий счётчик: один согласованный визит на RU и EN, hostname/page URL, отсутствие дубля, отказ/отзыв. Затем проверить цели по карте новых адресов. Внешние отчёты, настройки целей и GA/GTM нельзя объявить проверенными по одному frontend-тесту. Если существующий GA/GTM подтвердится, подключение потребует того же согласия и проверки дублей, без выдуманного ID.

Тест Steam return охватывает 12 новых/old/native адресов: сохраняются язык, ID и query, fragment не отправляется, внешние return URL запрещены существующим механизмом. Реальный Steam start/callback не вызывался: GET start создаёт login state, это не read-only проверка. После публикации проверить фактический вход, возврат на профиль/кабинет RU/EN, выход и права модерации/Portal Ops только для реально разрешённых аккаунтов. Backend/auth allowlist не менялся.

## Откат

До включения сохранить IDs добавленных правил/списка и полный текущий backup. При проблеме отключить **только** ASG migration rules; не заменять целиком entrypoint и не удалять используемый список. Возвращать прежний proxy/SSL только по сохранённой конфигурации и после проверки выдачи origin. Проверить отсутствие влияния на API-поддомены.

Для сайта использовать подготовленный шагом 4 fallback старого интерфейса под новыми RU-root/EN URL. Не вводить обратный `/` → `/ru/`: ранее закэшированный `/ru/` → `/` может создать цикл. Отключение правила не отзывает уже сохранённый 301 у всех клиентов. Проверить прямые новые targets, query, Steam и consent после отката. Не делать глобальную очистку Cloudflare cache, если достаточно согласованных URL.
